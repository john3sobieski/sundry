## Цель

Оффлайн-first десктопное приложение «всё в одном» для повседневных задач: изображения, векторизация, конвертеры, текст, файлы, разработка. Проект долгосрочный, поэтому главный приоритет — **архитектура, в которую новый инструмент добавляется одним модулем**, а не переписыванием ядра.

**Критерий приёма инструмента в проект** (чтобы не утонуть в feature creep):
1. работает локально, без обязательного интернета (исключение: курсы валют, с кэшем);
2. результат детерминирован и проверяем тестами;
3. реально нужен, а не «ещё один тулзик ради списка».

## Стек

- Язык: **Rust**
- UI: **Slint** (уже используется в Radiant PC)
- Цели: **сначала Windows**, затем **Android** (этап 10). Linux не планируем, но и не ломаем без необходимости (не использовать Windows-only API в ядре).
- Аудитория: публичный проект, в том числе для учебных задач (например, школьная информатика: перевод КБ ↔ Мбит и т.п.). Отсюда требования: понятные результаты, русский и английский интерфейс, запуск без установки и прав администратора.
- Векторизация: **алгоритмический трейсинг** (`vtracer` для цветных, `potrace`-подход для ч/б). Нейросетевой SVG отложен в бэклог как опциональный модуль.

## Архитектура

Cargo workspace:

```
sundry/
  Cargo.toml                # workspace
  PROGRESS.md
  crates/
    core/                   # без UI: трейт Tool, реестр, параметры, ошибки, Job (прогресс + отмена), настройки
    tools-image/            # ресайз, конвертация, скругление, сжатие, метаданные
    tools-vector/           # vtracer, оптимизация SVG, растеризация (resvg)
    tools-convert/          # данные, валюты, единицы, время, цвета
    tools-text/             # (позже) текст, кодировки, хэши, форматтеры
    tools-files/            # (позже) архивы, PDF, массовое переименование
    cli/                    # консольный фронтенд: тестировать любой тул без UI
    app/                    # Slint-приложение
```

Принципы:
- Каждый инструмент реализует трейт `Tool` (id, название, категория, описание параметров, `run(input, params, &Job) -> Result`). UI строится по описанию параметров, а не вручную под каждый тул, так новые тулы не требуют новой вёрстки.
- Тяжёлые зависимости (`ort`, ffmpeg, OCR, PDF-рендер) только за **cargo feature flags**: иначе время сборки и размер exe раздуются.
- **Ядро работает с байтами/потоками, а не с путями файлов.** На Android доступ к файлам идёт через Storage Access Framework (URI/дескрипторы), поэтому чтение и запись файлов живут в тонком слое платформы (`platform` trait), а не внутри тулов.
- Всё Windows-специфичное (контекстное меню, реестр, drag-and-drop окна) изолировано в отдельном модуле за `cfg(windows)`.
- Зависимости на C/C++ (mozjpeg, libwebp и т.п.) усложняют кросс-компиляцию под Android NDK: при выборе кодека проверять, собирается ли он под `aarch64-linux-android`.
- Долгие операции идут в фоновом потоке, с прогрессом и отменой, UI не блокируется.
- Весь код ядра покрыт тестами, на CLI можно прогнать любой тул без UI.
- Пакетная обработка и пайплайны (цепочки тулов) закладываются в ядро сразу, а не пристраиваются потом.

## Журнал решений

- Ядро (этап 1): `Tool::run(&Input, &Params, &Job) -> Result<Output>`. `Input`/`Output` это списки `Item` (данные + имя), чтобы позже без смены трейта поддержать несколько файлов на входе/выходе и цепочки тулов (выход одного = вход следующего). Файловых путей в тулах нет.
- Параметры проверяет реестр (`resolve`), а не сам тул: тул получает полный и валидный набор, неизвестные параметры отвергаются. Пресеты/пайплайны этапа 8 будут хранить `Params`.
- Подписи в UI не живут в ядре: у `ToolInfo` английские `name`/`description` как запасной вариант, локализация по ключам от `id` (`tool.<id>.name` и т.п.). Допустимый `id`: `a-z`, `0-9`, `.`, `-`, `_`.
- Настройки: TOML, неизвестные поля игнорируются, отсутствующие берут значения по умолчанию. Запись через временный файл и rename. Портативный режим: маркер-файл `sundry.portable` рядом с exe.
- Логирование: `tracing`; фильтрация по `RUST_LOG` (feature `env-filter`) пока не включена, чтобы не тянуть лишние зависимости.
- `cargo-deny`: белый список MIT, Apache-2.0 (+LLVM-exception), BSD-2/3, ISC, Zlib, Unicode-3.0, CC0-1.0. MPL-2.0 и прочие слабые копилефты не включены, добавлять осознанно.
- `rustfmt.toml`: `use_small_heuristics = "Max"` (короткие структуры в одну строку).
- Векторизация: алгоритмический трейсинг (vtracer/potrace-подход). Нейро-SVG отложен: для логотипов и иконок трейсинг не хуже, быстрее и без GPU. Целевая машина (GTX 1080, Pascal) для современных VLM-моделей неудобна.

Интерактивной рамки выделения в просмотрщике нет: область задаётся числами.
- Форматирование: в песочнице не было `rustfmt`, код отформатирован вручную. Один раз запустить workflow `Format`.

Код пункта «конвертер данных» и всё, что помечено «до сборки не проверено», в Actions ещё не прогонялось.


Что есть в `crates/core` (пакет `sundry-core`):
- `error.rs`: единый `Error` (thiserror), `Result<T>`
- `data.rs`: `Data` (Empty/Text/Bytes), `Item` (данные + необязательное имя), `Input`/`Output` (списки `Item`)
- `params.rs`: `ParamSpec`/`ParamKind` (bool, int, float, text, choice), `Value`, `Params` с типизированными геттерами, `resolve()` (валидация, значения по умолчанию, отказ на неизвестные параметры)
- `tool.rs`: трейт `Tool` (`info`, `params`, `run`), `ToolInfo`, `Category`
- `registry.rs`: `Registry` (регистрация с проверкой определения, `get`, `iter`, `by_category`, `search`, `run`)
- `job.rs`: `Job` (клонируемый хэндл на атомиках: прогресс 0..1 и отмена)
- `settings.rs`: `Settings` (язык, тема, уровень логов) в TOML; путь: рядом с exe при наличии файла `sundry.portable`, иначе `%APPDATA%\Sundry\settings.toml`
- `logging.rs`: `init(LogLevel)` на `tracing` + `tracing-subscriber`, вывод в stderr
- Тесты: модульные в каждом файле и сквозной `tests/registry_flow.rs` с примером тула

Что есть в `crates/cli` (пакет `sundry-cli`, бинарник `sundry`), без новых зависимостей (только `sundry-core` и `thiserror`):
- `main.rs`: аргументы, настройки, логирование, реальные stdin/stdout/stderr, код выхода
- `lib.rs`: `run()`, `Io`, текст справки
- `args.rs`: разбор командной строки (`list`, `info`, запуск тула, `--help`, `--version`), модульные тесты
- `commands.rs`: `list` (таблица, фильтр `-c` по категории и поиск по строке) и `info` (описание и параметры)
- `runner.rs`: типизация `-p` по `ParamSpec`, чтение входа, запись результата, защита от перезаписи и от выхода за папку
- `builtin.rs`: `registry()`, сюда каждый крейт с тулами добавляет свою регистрацию
- `tests/cli.rs`: сквозные тесты (вывод, коды выхода, файлы, stdin, ошибки)

Что есть в `crates/app` (этап 3, пункты 1-2): окно с категориями слева (счётчики по текущему поиску), поиском сверху (Ctrl+K), списком тулов и панелью описания, строкой состояния с выбором темы (сохраняется в настройки). Компоненты `SButton`, `SField`, `SSelect`, `SSwitch` готовы; `SButton`/`SSwitch` пока нигде не используются (пригодятся для автоформы). Реестр берётся из `sundry_cli::builtin::registry()` (сейчас там `convert.data`).

Что есть в `crates/tools-image`: тулы `image.resize`, `image.convert`, `image.round_corners`, `image.crop`, общий кодек (`codec.rs`, там же `Target`), геометрия ресайза (`plan.rs`), превью (`preview.rs`).
