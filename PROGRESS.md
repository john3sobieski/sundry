## Правила работы (от владельца)

- Владелец сам не программирует, всё делается вместе с ИИ. Объясняй коротко, но термины не упрощай.
- Если что-то неясно, **спрашивай, а не додумывай**.
- Ничего не компилируй и не пытайся. Сборка и компиляция всегда без cargo, ТОЛЬКО с помощью Git Actions.
- Большие задачи делить на этапы, один этап за раз.
- Проект **публичный**: комментарии в коде, README, сообщения коммитов и docs-строки на английском, комментарий максимум 1-2 строки.
- После любых правок кода в конце ответа: одно простое название коммита на английском.
- Изменено ≤5 файлов → отдавать отдельно; >5 → zip. JS-файлы всегда в zip. Всегда указывать путь файла в репозитории.
- Замеченные по дороге баги и проблемы безопасности называть, если проверка дешёвая.
- Личные данные (ФИО, страна) не упоминать и не спрашивать. Автор в лицензиях и метаданных: GitHub-ник `john3sobieski`.
- Версии крейтов и API не брать по памяти: сверяться с crates.io / docs.rs перед добавлением зависимости.
- **Лицензии зависимостей:** проект под PolyForm Noncommercial (не GPL-совместимая, не OSI open source). Перед добавлением крейта проверять его лицензию; GPL/AGPL-зависимости не подключать (в том числе в виде статической линковки C-библиотек). Добавить `cargo-deny` в CI с белым списком лицензий (MIT, Apache-2.0, BSD, ISC, Zlib и т.п.). Для потрассировки ч/б проверить лицензию выбранной реализации: оригинальный `potrace` под GPL.

## Цель

Оффлайн-first десктопное приложение «всё в одном» для повседневных задач: изображения, векторизация, конвертеры, текст, файлы, разработка. Проект долгосрочный, поэтому главный приоритет — **архитектура, в которую новый инструмент добавляется одним модулем**, а не переписыванием ядра.

**Критерий приёма инструмента в проект** (чтобы не утонуть в feature creep):
1. работает локально, без обязательного интернета (исключение: курсы валют, с кэшем);
2. результат детерминирован и проверяем тестами;
3. реально нужен, а не «ещё один тулзик ради списка».

## Стек

- Язык: **Rust**
- UI: **Slint** (уже используется в Radiant PC)
- Цели: **сначала Windows**, затем **Android** (этап 10). Linux не планируем, но и не ломаем без необходимости (не использовать Windows-only API в ядре).
- Аудитория: публичный проект, в том числе для учебных задач (например, школьная информатика: перевод КБ ↔ Мбит и т.п.). Отсюда требования: понятные результаты, русский и английский интерфейс, запуск без установки и прав администратора.
- Векторизация: **алгоритмический трейсинг** (`vtracer` для цветных, `potrace`-подход для ч/б). Нейросетевой SVG отложен в бэклог как опциональный модуль.

## Архитектура

Cargo workspace:

```
sundry/
  Cargo.toml                # workspace
  PROGRESS.md
  crates/
    core/                   # без UI: трейт Tool, реестр, параметры, ошибки, Job (прогресс + отмена), настройки
    tools-image/            # ресайз, конвертация, скругление, сжатие, метаданные
    tools-vector/           # vtracer, оптимизация SVG, растеризация (resvg)
    tools-convert/          # данные, валюты, единицы, время, цвета
    tools-text/             # (позже) текст, кодировки, хэши, форматтеры
    tools-files/            # (позже) архивы, PDF, массовое переименование
    cli/                    # консольный фронтенд: тестировать любой тул без UI
    app/                    # Slint-приложение
```

Принципы:
- Каждый инструмент реализует трейт `Tool` (id, название, категория, описание параметров, `run(input, params, &Job) -> Result`). UI строится по описанию параметров, а не вручную под каждый тул, так новые тулы не требуют новой вёрстки.
- Тяжёлые зависимости (`ort`, ffmpeg, OCR, PDF-рендер) только за **cargo feature flags**: иначе время сборки и размер exe раздуются.
- **Ядро работает с байтами/потоками, а не с путями файлов.** На Android доступ к файлам идёт через Storage Access Framework (URI/дескрипторы), поэтому чтение и запись файлов живут в тонком слое платформы (`platform` trait), а не внутри тулов.
- Всё Windows-специфичное (контекстное меню, реестр, drag-and-drop окна) изолировано в отдельном модуле за `cfg(windows)`.
- Зависимости на C/C++ (mozjpeg, libwebp и т.п.) усложняют кросс-компиляцию под Android NDK: при выборе кодека проверять, собирается ли он под `aarch64-linux-android`.
- Долгие операции идут в фоновом потоке, с прогрессом и отменой, UI не блокируется.
- Весь код ядра покрыт тестами, на CLI можно прогнать любой тул без UI.
- Пакетная обработка и пайплайны (цепочки тулов) закладываются в ядро сразу, а не пристраиваются потом.

## Журнал решений

- Ядро (этап 1): `Tool::run(&Input, &Params, &Job) -> Result<Output>`. `Input`/`Output` это списки `Item` (данные + имя), чтобы позже без смены трейта поддержать несколько файлов на входе/выходе и цепочки тулов (выход одного = вход следующего). Файловых путей в тулах нет.
- Параметры проверяет реестр (`resolve`), а не сам тул: тул получает полный и валидный набор, неизвестные параметры отвергаются. Пресеты/пайплайны этапа 8 будут хранить `Params`.
- Подписи в UI не живут в ядре: у `ToolInfo` английские `name`/`description` как запасной вариант, локализация по ключам от `id` (`tool.<id>.name` и т.п.). Допустимый `id`: `a-z`, `0-9`, `.`, `-`, `_`.
- Настройки: TOML, неизвестные поля игнорируются, отсутствующие берут значения по умолчанию. Запись через временный файл и rename. Портативный режим: маркер-файл `sundry.portable` рядом с exe.
- Логирование: `tracing`; фильтрация по `RUST_LOG` (feature `env-filter`) пока не включена, чтобы не тянуть лишние зависимости.
- `cargo-deny`: белый список MIT, Apache-2.0 (+LLVM-exception), BSD-2/3, ISC, Zlib, Unicode-3.0, CC0-1.0. MPL-2.0 и прочие слабые копилефты не включены, добавлять осознанно.
- `rustfmt.toml`: `use_small_heuristics = "Max"` (короткие структуры в одну строку).
- Векторизация: алгоритмический трейсинг (vtracer/potrace-подход). Нейро-SVG отложен: для логотипов и иконок трейсинг не хуже, быстрее и без GPU. Целевая машина (GTX 1080, Pascal) для современных VLM-моделей неудобна.
- CLI (этап 2): крейт `crates/cli` (`sundry-cli`, бинарник `sundry`) = тонкий `main.rs` + библиотека с функцией `run(registry, args, &mut Io) -> u8`: потоки подменяются в тестах. Парсер аргументов самописный, без `clap`: параметры тулов динамические (берутся из `ParamSpec`), и лишняя зависимость не нужна.
- CLI: параметры тула передаются только как `-p имя=значение` (голое `-p имя` = bool `true`), а не как `--имя значение`: так параметры тулов никогда не конфликтуют с флагами самого CLI (`-i`, `-o`, `-t`, `-f`). Менять дёшево.
- CLI: вход через `-i FILE` (`-` = stdin) и `-t TEXT`, можно повторять. Вывод без `-o`: только текст в stdout, бинарный результат отклоняется (чтобы не сыпать мусор в терминал). `-o PATH`: файл, либо папка (для нескольких результатов), `-o -` = сырые байты в stdout. Существующие файлы без `--force` не перезаписываются, проверка до начала записи. Имя файла от тула (`Item::name`) считается недоверенным: берётся только последний компонент, выйти из папки нельзя.
- CLI: слова `help`, `info`, `list` зарезервированы под команды, id тула не может быть таким (тест в `builtin.rs`). Коды выхода: 0 успех, 1 сбой, 2 ошибка в команде (включая неверные параметры и неизвестный тул).
- CLI: сообщения только на английском, локализация придёт с UI (этап 3). Битый файл настроек в CLI не останавливает работу: предупреждение в stderr и значения по умолчанию.
- CLI: `demo` (feature, выключена по умолчанию) регистрирует учебный тул `text.repeat`, чтобы можно было пощупать CLI до появления настоящих тулов. Когда появится конвертер данных (этап 3), удалить `demo.rs` и feature, а тесты `tests/cli.rs` перевести на него.
- Стилистика UI (утверждено владельцем): светлая и тёмная (OLED) темы обязательны, режим «Авто» следует за системой. Палитра строго чёрно-белая; зелёный/жёлтый/красный только для прогресса, успеха, предупреждения, ошибки (всегда дублируются текстом или иконкой). Вид промышленный, не «ИИ-приложение»: радиус 4 px, рамки 1 px вместо теней, без градиентов, блюра, свечения, эмодзи и иллюстраций; иерархия весом, размером, отступами и рамками, не оттенками цвета.
- Токены (тёмная / светлая): `bg` #000000 / #FFFFFF; `surface` #0A0A0A / #F5F5F5; `raised` #141414 / #FFFFFF; `text` #EDEDED / #0A0A0A; `text-2` #A3A3A3 / #525252; `text-3` #8A8A8A / #737373; `divider` #262626 / #E0E0E0; `control-border` #666666 / #8A8A8A; `success` #3FB950 / #1A7F37; `warning` #D29922 / #9A6700; `error` #F85149 / #CF222E. Контраст текста выше 4,5:1, границ элементов управления не меньше 3:1 (считалось по формуле WCAG, на реальном экране перепроверить). Главная кнопка инвертирована (белая на тёмной, чёрная на светлой), фокус: рамка 2 px цвета `text`.
- Типографика: системные шрифты (Segoe UI на Windows, Roboto на Android), моноширинный для результатов, ID, чисел и путей, табличные цифры. Размеры 12/13/15/20 px, базовый 13, вес до 600.
- Раскладка: слева категории, сверху поиск (Ctrl+K), по центру форма параметров и результат, снизу строка состояния с прогрессом и отменой. На Android тот же каркас в один столбец (этап 10). Выбранный пункт отмечается маркером (полоса слева), а не оттенком серого.
- Анимации: 100-150 мс, `ease-out`, только цвет и прозрачность (ховер, фокус, смена темы, появление результата); прогресс-бар показывает реальный `Job::progress`; без пружин, отскоков и каскадов.
- Иконки: одна толщина линии (1,5 px), без заливок. Набор и его лицензию выбрать и проверить до добавления (`cargo-deny` ассеты не проверяет).
- UI-оболочка (этап 3, пункты 1-2): крейт `crates/app` (`sundry-app`), Slint 1.17.1 (сверено по docs.rs/GitHub). Файлы: `ui/theme.slint` (глобал `Theme`, токены), `ui/strings.slint` (названия категорий через `@tr`), `ui/components/{button,field,select,switch}.slint`, `ui/app-window.slint`, `src/main.rs`. Исключение: `ListView` из std-widgets (скроллбар в стиле fluent, перерисовать позже).
- Тема: `Theme.mode` (system/light/dark) хранится в `Settings.theme` (Auto/Light/Dark). В режиме system тёмная тема включается, если `Palette.color-scheme == dark`. **Не проверено на реальной системе**, что значение отражает тему Windows; если нет, брать тему другим способом.
- Slint: у `Text` нет настройки табличных цифр (font-feature), поэтому числа выводятся моноширинным шрифтом (`Theme.mono`, пока `Consolas`; на Android заменить/вшить шрифт). Настройки «уменьшить анимацию» в документации Slint не найдено, анимации короткие (120 мс) и только цвет/позиция маркера.
- Крейт `app` использует `unsafe_code = "deny"`, а не workspace-`forbid`: `forbid` нельзя ослабить для кода, который генерирует Slint. Код самого приложения unsafe не содержит.

## Сделано

Этапы 0, 1, 2 и пункты 1-2 этапа 3 написаны, **но ещё ни разу не собирались**: в среде, где писался код, не было ни `cargo`, ни сети.

**Первое действие следующей сессии:** владелец запускает `cargo fmt --all`, `cargo clippy --workspace --all-targets --all-features`, `cargo test --workspace`, `cargo deny check` и присылает вывод ошибок. Исправить всё найденное до начала этапа 3. Заодно руками проверить CLI: `cargo run -p sundry-cli --features demo -- list`, затем `-- text.repeat -t ab -p times=3`.

Что есть в `crates/core` (пакет `sundry-core`):
- `error.rs`: единый `Error` (thiserror), `Result<T>`
- `data.rs`: `Data` (Empty/Text/Bytes), `Item` (данные + необязательное имя), `Input`/`Output` (списки `Item`)
- `params.rs`: `ParamSpec`/`ParamKind` (bool, int, float, text, choice), `Value`, `Params` с типизированными геттерами, `resolve()` (валидация, значения по умолчанию, отказ на неизвестные параметры)
- `tool.rs`: трейт `Tool` (`info`, `params`, `run`), `ToolInfo`, `Category`
- `registry.rs`: `Registry` (регистрация с проверкой определения, `get`, `iter`, `by_category`, `search`, `run`)
- `job.rs`: `Job` (клонируемый хэндл на атомиках: прогресс 0..1 и отмена)
- `settings.rs`: `Settings` (язык, тема, уровень логов) в TOML; путь: рядом с exe при наличии файла `sundry.portable`, иначе `%APPDATA%\Sundry\settings.toml`
- `logging.rs`: `init(LogLevel)` на `tracing` + `tracing-subscriber`, вывод в stderr
- Тесты: модульные в каждом файле и сквозной `tests/registry_flow.rs` с примером тула

Что есть в `crates/cli` (пакет `sundry-cli`, бинарник `sundry`), без новых зависимостей (только `sundry-core` и `thiserror`):
- `main.rs`: аргументы, настройки, логирование, реальные stdin/stdout/stderr, код выхода
- `lib.rs`: `run()`, `Io`, текст справки
- `args.rs`: разбор командной строки (`list`, `info`, запуск тула, `--help`, `--version`), модульные тесты
- `commands.rs`: `list` (таблица, фильтр `-c` по категории и поиск по строке) и `info` (описание и параметры)
- `runner.rs`: типизация `-p` по `ParamSpec`, чтение входа, запись результата, защита от перезаписи и от выхода за папку
- `builtin.rs`: `registry()`, сюда каждый крейт с тулами добавляет свою регистрацию
- `demo.rs`: учебный тул `text.repeat` (feature `demo`)
- `tests/cli.rs`: сквозные тесты (вывод, коды выхода, файлы, stdin, ошибки)

Что есть в `crates/app` (этап 3, пункты 1-2): окно с категориями слева (счётчики по текущему поиску), поиском сверху (Ctrl+K), списком тулов и панелью описания, строкой состояния с выбором темы (сохраняется в настройки). Компоненты `SButton`, `SField`, `SSelect`, `SSwitch` готовы; `SButton`/`SSwitch` пока нигде не используются (пригодятся для автоформы). Без `--features demo` реестр пуст и список показывает «No tools are registered yet».
